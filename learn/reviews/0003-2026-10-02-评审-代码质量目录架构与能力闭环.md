# 代码质量、目录架构与能力闭环评审

首次评审：2026-10-02。基线：`b8c98ee`。本次不修改生产代码。

## 结论

项目有真实实现、基本合理的领域划分和大量有效测试；不是只有 UI、接口和宣传的空壳。但高级能力的完成度明显低于 README 的表述，存在“模块已经写出并测过，就被当作产品能力已经交付”的问题。更适合定位为有工程基础、尚未完成集成收口的实验性 Agent 内核，而非成熟可靠的通用底座。

不能从代码反推作者是否使用 AI，也不能认定 AI 生成比例。“vibe coding”若指缺乏整体约束的功能叠加，则确实有相应工程症状：局部契约丰富、全局闭环不足；阶段编号与修补历史大量进入代码；可选依赖和宽泛异常处理使装配问题不易暴露；功能宣传领先于默认运行路径。

## 高优先级发现

### 1. 产物导出未限制解析后的源路径和目标路径（P1）

位置：[sandbox_middleware.py](../../poirot/backend/agents/middlewares/sandbox_middleware.py) 第 127–193 行；[docker_path_translator.py](../../poirot/backend/agents/sandbox/translators/docker_path_translator.py) 第 34 行起。

`_register_artifacts` 仅检查虚拟路径字符串前缀，将剩余部分直接用于 host 路径与 `outputs_dir / filename`。反向翻译也不归一化和检查归属。输入 `/mnt/poirot/user-data/../probe.txt` 可以逃出当前 sandbox 子目录；目标同样逃出 `outputs/`。

实测：在临时目录建立 `sandboxes/s1` 和 `sandboxes/probe.txt`，以 DockerPathTranslator + SandboxMiddleware 实际导出方法执行上述路径。结果 `project/.poirot/probe.txt` 被创建，注册下载产物 1 个。源和目标均越过各自预期边界。未触碰真实工作区数据。

这不是容器内的普通写入限制：导出代码运行于宿主。应分别规范化源与目标、验证各自根目录归属、处理符号链接，并在路径翻译失败时拒绝而非拼接降级。

### 2. wheel 漏打包运行必需资源（P1，影响非 editable 安装）

位置：[pyproject.toml](../../pyproject.toml) 第 28–29 行；[prompts/manager.py](../../poirot/backend/agents/prompts/manager.py) 的 `_read`。

成功构建的 wheel 包含 **564 个 Python 文件，其中 249 个位于 tests**；但 prompt Markdown、内置 SKILL.md、profiles YAML、TypeScript 专家桥接文件均为 **0 个**。隔离加载 `get_prompt_manager().load('leader', 'identity')` 得到 `FileNotFoundError: prompt not found: leader/identity`。

源码 editable 安装绕过了这个交付缺陷。应显式声明包数据，排除测试包，增加脱离源码目录的 wheel 安装冒烟验证。构建成功本身不足以验收。

### 3. 长期记忆存储可以丢失其他实例已写入的数据（P1，共享目录多实例）

位置：[memory store](../../poirot/backend/agents/memory/strategies/default/store.py) 第 225–292 行。

每个实例启动时加载自己的内存索引，`threading.Lock` 仅保护本实例；更新时以 `open(..., 'w')` 将本实例索引全量重写。两个实例同时使用默认共享目录时，后写入的独立记忆会被旧快照覆盖。

实测：A、B 先同时打开同一目录；A 添加 a1，B 添加 b2；重新打开能看到 b2；A 更新 a1 后，重新打开已找不到 b2。这个复现不需要真正并发，只需要两个存活实例。

此外，全量原地覆写存在中途写失败/进程退出造成截断的风险，此项是静态风险判断，未注入磁盘故障。解决需包括跨实例一致性、锁内重载/事务和原子替换；单独增加一把跨进程锁仍不能修复旧快照覆盖。

## 能力闭环与表述偏差

### 4. 多 Agent 自动进化与评估是部分组件实现，标准装配不可用（P2）

位置：[evolution/bootstrap.py](../../poirot/backend/agents/multiagent/evolution/bootstrap.py) 第 77–100 行；[eval/bootstrap.py](../../poirot/backend/agents/multiagent/eval/bootstrap.py) 第 67–87 行。

标准装配明确传 `llm_caller=None`，评估器为 `evaluator=None` / `judge_fn=None`。EvolutionMutator 遇到空调用器返回失败，原因 `no LLM caller configured`，分类却标为 `llm_timeout`；这还会把配置缺失误归因为超时。评估适配器同样返回未配置失败。

版本 DAG、门控、指标和工作线程并非空壳，但“打开开关即可形成真实自动进化闭环”不成立。L2 装配和 L3 装配还分别创建一套空评估 registry/bridge，增加后续注入不一致的风险。相关 CLI 模块也保留直接抛 `NotImplementedError` 的入口；不应将这些骨架描述为已交付用户能力。

### 5. Skill 自动触发与自动回滚没有生产调用点（P2）

位置：[EvolutionManager.run_cycle](../../poirot/backend/agents/skill/evolution/manager.py) 第 49 行；[GitRatchet.check_and_rollback](../../poirot/backend/agents/skill/evolution/gates/git_ratchet.py) 第 28 行；[app/bootstrap.py](../../poirot/backend/app/bootstrap.py) 第 330–411 行。

搜索 agents/app 中 `run_cycle(` 和 `check_and_rollback(`，只有方法定义。装配确实创建 EvolutionManager，CLI 也有手动 `evolve_skill` 调用，但没有自动调度循环，也没有装配和调度 GitRatchet。

因此应区分“手动进化组件可运行”和“阈值触发自动进化、退化自动回滚已接通”。README 当前混用了这两个层次。

Skill 进化默认门控评估的是候选 SKILL 文本的格式、关键词和规则通过率。即使开启当前 RegistryEvalBridge，核心路径仍然读取 SKILL 文本交给 ResponseContractChecker。它不能单独证明应用新 Skill 后真实研究任务质量提升。独立的任务质量分析器存在，不代表已经构成候选与基线对照实验。

### 6. Docker 写入白名单是弱约束（P2）

位置：[docker_path_guard.py](../../poirot/backend/agents/sandbox/guards/docker_path_guard.py) 第 25–43 行。

已验证 `validate_path('/mnt/poirot/user-data/../../../tmp/review-probe', write=True)` 不报错；`echo hello > "/tmp/review-probe"` 也通过命令校验。`tee` 和相对路径不校验是代码明确记录的限制。

不能据此声称已经“强制所有写入落在持久化挂载区”。也不能将该复现称为 Docker 容器逃逸：这里证明的是 guard 失效，容器隔离是另一个边界。第 1 项则是独立且更严重的宿主导出边界问题。

## 架构与目录评价

### 合理且值得保留的部分

- `app` 负责 CLI/TUI/装配，`agents` 按 memory、sandbox、skill、multiagent、context_engineering 等领域划分，有明确主干，不是所有功能塞进一个文件。
- LeaderAgent 是调用已编译图、收集报告与保存产物的薄封装；middleware 有实际生命周期挂载。
- Sandbox 组合 Runtime、Translator、Guard，`validate → translate → execute → mask` 的边界清楚，利于独立替换实现。
- memory 有真实 Markdown 持久化、BM25 索引和衰减；Skill 有真实 SQLite 与版本记录；这些都不是用名词包装的空接口。
- 测试不全是 mock 对 mock：最小 Agent 集成测试使用 fake 模型，但运行实际图、运行记录和报告文件链路。以 fake 模型保证确定性本身合理。

### 目录和边界的问题

- **单向依赖承诺已经破坏**：[sandbox_middleware.py](../../poirot/backend/agents/middlewares/sandbox_middleware.py) 第 137 行从 app.bootstrap 导入私有 `_PROJECT_ROOT`。领域 middleware 反向依赖应用装配，说明输出路径应作为依赖注入。AST 绝对导入扫描找到这一处，不声称已识别所有动态依赖。
- **复杂度集中在连接层**：生产 Python（agents/app）共 313 文件、34,033 行（含注释/空行）；测试 249 文件、35,428 行。`bootstrap.py` 675 行，`StreamService.stream` 287 行，`_cmd_skill` 289 行。行数不是缺陷判据，但这些函数同时承担多种职责，应成为维护检查重点。
- 模型切换、模式切换、MCP 重载重复传递大量构造参数，遗漏一个 middleware/配置即可形成模式差异，已有大量补漏注释。应集中构建 runtime 依赖对象，而不是继续复制装配参数表。
- `memory/bootstrap.py` 通过运行时替换 store.add/update 等方法连接索引；`app/bootstrap.py` 直接替换 `evo._eval_bridge` 私有字段。能运行，但依赖关系不再由明确构造协议表达，后续维护者容易漏掉装配步骤。
- `app/gateway`、`app/schemas`、`capabilities/models` 当前只有极小的初始化文件；单后端项目额外的 backend 层本身无害，空目录却不应被当作架构完成度。适宜删除无用途的预留层，而非整体搬家。
- 文档在根 USAGE、resource 下多语言使用说明、learn 中分布；当前缺少 docs 主目录。learn 导航逐项累积变更，与“简短分类导航”的仓库约束不符。应小步收敛入口和长期说明，不必为了整齐重排全部生产代码。

### 命名和可维护性

- `HybridRetriever` 当前是纯 BM25，默认 `text.lower().split()`，无中文分词；中英文名称与实际支持范围应写清。已确认实现，未做中文召回率基准，不能给出质量比例。
- InMemorySaver 仅进程内保留会话，不等同重启恢复；磁盘报告/长期记忆也不等同完整会话检查点。
- AST 发现 163 处捕获 Exception/BaseException 或裸 except。数值只是定位线索，不等于 163 个 bug。明确的问题例子是 Skill EvolutionManager 在创建版本失败时仍保留 accept 决策，并吞掉记录失败；诊断时难以区分“接受候选”和“成功发布版本”。
- 注释大量引用 `Batch`、`INV`、`D12`、`42 文档` 等阶段术语，部分设计目录未随仓库交付。这使注释表达了约束，却没有给维护者可查验的完整来源。当前行为、原因和限制比开发过程编号更值得保留在代码里。

## 为什么测试全绿仍存在上述问题

1. 默认 suite 排除了 integration marker 的真实依赖测试，且部分集成模块缺依赖会跳过；“全绿”是该环境、该测试集合的结论。
2. 多 Agent 装配测试有一类只断言 `version_dag / worker / mutator is not None`，没有验证“通过应用装配创建组件后，真实依赖可用并完成一次候选评估”。参见 [test_bootstrap.py](../../poirot/backend/tests/v1/unit/multiagent/evolution/test_bootstrap.py) 第 34 行。
3. Skill 的测试可以显式调用 evolve/run_cycle，通过不代表应用生命周期会自动调用它们。
4. 源码内 pytest 不会自然发现 wheel 资源漏打包；单实例存储测试也不会自然发现两个独立内存快照覆盖。
5. 仓库没有 `.github` 工作流，pyproject 无统一 lint/type-check 配置，未见依赖锁文件；当前结果仍依赖本机人工执行。不是所有个人原型都需要复杂 CI，但当前宣传的复杂度已经需要可重复验收。

## 建议的处理顺序

1. 修复产物源/目标路径边界、记忆多实例数据一致性、wheel 资源打包；为这些已复现行为添加回归验证。
2. 将 README 能力分为已接通、手动可用、实验性组件、未实现，并明确持久化、中文召回、Docker/Local 的实际边界。
3. 为保留的高级能力补完整装配验收；暂时没有真实 evaluator 的进化功能，应在启用时明确报配置缺失，而不是启动无法工作的后台线程。
4. 再集中 runtime 装配、清除反向依赖和无用途的预留目录。保留有效领域划分，不建议推倒重写。
5. 建立最小持续检查：默认测试、wheel 安装与资源加载、路径边界、多实例存储；真实 LLM/Docker 验收另设显式入口与成本约束。
