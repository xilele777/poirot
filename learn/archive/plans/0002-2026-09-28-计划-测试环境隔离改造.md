# 测试环境隔离改造

日期：2026-09-28
类型：计划
关联：[测试隔离质量评审](../reviews/0001-2026-09-28-评审-测试隔离质量.md)

## 背景与问题

多次全量验收都在测试上出问题。独立查证结论：测试**覆盖**优秀（221 个测试文件、
2700+ 用例），但**进程级环境隔离从未被立成项目级约束**。表现为：

1. 整个 `tests/` 树**零 `conftest.py`**，没有集中的隔离设施，各文件纪律参差。
2. **"单元测试"混入外部依赖**：`test_stage5/6_integration.py` 需真实 Docker +
   13GB 镜像却放在 `unit/sandbox/`；`test_default_strategy_e2e.py` 在**模块导入时**
   `load_dotenv()`；`test_pi_installer.py` 依赖宿主 `shutil.which("npm")`。
3. **对宿主机器有隐含假设**：假设 Linux、假设未装 npm、假设未设凭据变量、假设无 `.env`。
4. **隔离是补丁式的**：污染源（e2e 模块级 `load_dotenv`）仍在，只在受害方
   （`test_provider_config.py`）加挡板 fixture。

现成标本（本机当前实测）：

```
6 failed, 2720 passed, 3 skipped
FAILED v1/unit/sandbox/test_stage5_integration.py  (3)
FAILED v1/unit/sandbox/test_stage6_integration.py  (3)
```

失败原因：`shutil.which("docker")` 命中（CLI 在），但 Docker 守护进程未运行，
守卫只判断 CLI 存在与否，于是"应跳过"退化为"硬失败"。根因同属"对宿主环境有
隐含假设 + 分层缺失"。

## 目标

让"全量验收"有一条**纯净、可重复、与宿主环境无关**的基线：

- 默认 `python -m pytest poirot/backend/tests/ -q` 不因宿主环境差异而失败或漏跑；
- 测试之间不通过 `os.environ` / `sys.modules` 互相渗透；
- 需真实外部依赖的用例显式分层，默认不参与，可单独按需运行。

非目标：不重写测试内容，不追求把用例转到 `integration/` 物理目录（用 marker
分层，改动更小更可逆）。

## 阶段一：建立项目级隔离层

新增 `poirot/backend/tests/conftest.py`（`tests/` 下尚无 conftest，此文件覆盖
其全部子目录）。

- `_BASELINE_ENV`：conftest 导入时快照进程环境，作为基线参照。
- autouse fixture `_restore_environ`：每个测试前快照 `os.environ`，测试后精确还原，
  使任何直接 `os.environ[...] = ...` 都无法泄漏到后续测试（不依赖作者是否走
  `monkeypatch`）。
- autouse fixture `_drop_stub_modules`：测试期间新建的**假**可选依赖占位模块
  （无 `__file__` / `__path__`，如 `agent_sandbox`）在测试后从 `sys.modules` 移除，
  避免占位污染后续文件（与 `tests/v1/fixtures/sdk_stubs.py` 配套）。
- 提供 `env_file_scope` 辅助：需要 `.env` 的测试在**作用域内**临时注入变量并在
  退出时还原，替代模块级 `load_dotenv()` 的全局污染。

验证：全量套件通过数与阶段零一致（除阶段三将改动的 marker 外）。

## 阶段二：铲除污染源，撤掉受害方挡板

- `test_default_strategy_e2e.py`：删除模块级 `load_dotenv()`。改为用
  `dotenv_values()` **只读**读取 `.env` 来决定是否 skip，并在测试作用域内经
  `monkeypatch` 注入所需变量。保留"有真实 key 才跑"的原意，但不再全局污染。
- `test_provider_config.py`：删除下游挡板 fixture `_isolate_provider_model_env`
  及其注释——污染源已除，挡板成为冗余的"治标"痕迹。

验证：单跑 `test_provider_config.py` 通过；先跑 e2e 再跑 provider_config 仍通过
（证明隔离不再依赖挡板）。

## 阶段三：分层与默认门禁

- 在 `pyproject.toml` 注册 `integration` marker，并加
  `addopts = "-m 'not integration'"`，使默认全量运行排除集成层。
- 给以下用例打 `pytest.mark.integration`：
  - `unit/sandbox/test_stage5_integration.py`、`test_stage6_integration.py`（真实 Docker）
  - `integration/test_default_strategy_e2e.py`（真实 API key）

验证：
- `python -m pytest poirot/backend/tests/ -q` → 零失败（stage5/6 被排除）。
- `python -m pytest poirot/backend/tests/ -q -m integration` → 单独可运行；
  无 Docker 守护进程时**跳过而非报错**（阶段三顺带把 stage5/6 的守卫从
  "CLI 存在"升级为"守护进程可达"，见下）。

## 阶段四：文档落地与收尾

- 新增变更记录 `learn/changes/0008-...`。
- 更新 `learn/WORKLOG.md`（当日倒序置顶）、`learn/README.md` 索引。
- 在评审文档中标注根治建议的落地状态（建议 1/2/3 是否已执行）。
- 复核 `USAGE.md` / `resource/USAGE.*.md` 中的测试命令说明是否需同步（若新
  marker 影响用户命令则补一句）。

## 风险与回滚

- 每测试还原 `os.environ` 属强隔离，若某用例依赖"跨测试共享的环境变更"会暴露
  出来——这是期望行为（暴露即缺陷），但需在阶段一后立即全量验证。
- 默认排除 `integration` 会改变"全量"的语义，需在文档明确：完整门禁为
  `-m integration` 叠加默认运行。
- 全部改动可用 `git` 单次回滚（一个逻辑变更一个提交）。
